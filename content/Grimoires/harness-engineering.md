# ⚙️ Harness Engineering (治理工程) 教學指南

在之前的 [[Grimoires/context-engineering|🧠 Context Engineering (脈絡工程)]] 中，我們談到了如何賦予 AI 強大的背景知識，讓它不再是個「失憶大腦」。在打好基礎之後，接下來面臨的核心問題是：**「我們該如何確保這股強大的力量不會失控？」**

這正是 **Harness Engineering (治理工程)** 的核心價值。當大型語言模型 (LLM) 進化成可以使用外部工具改變現實世界的 AI 代理人 (Agent) 時，我們不能只依賴「它今天心情好所以回答正確」。我們必須為 AI 裝上方向盤與煞車系統。

---

## 一、為什麼需要治理工程？

AI 的運作核心是一個**機率分佈的統計模型 (Token Prediction)**，這代表給予同樣的輸入，它在不同的時間點依然可能會產生不同的輸出。

如果說 Prompt Engineering 和 Context Engineering 是用來處理「如何讓 AI 啟動並給出好答案」，那麼 Harness Engineering 則是將 AI 納入「真實軟體工程」的範疇：
- **可預測性 (Predictability)**：如何讓充滿隨機性的 AI，穩定提供結構化資料（如 JSON/XML）給後端系統。
- **安全性 (Security)**：當我們賦予 AI 下達指令的能力時，必須避免它意外執行 `rm -rf /` 這類毀滅性動作。
- **可測量性 (Measurability)**：當你修改了一段提示詞，你需要客觀的數據證明它「真的變好」了，而不是只是剛好在這個測資上表現不錯。

---

## 二、三大治理支柱

### 1. 輸出護欄與權限控制 (Guardrails & Permissions)
當我們讓 Agent 具備操作工具 (Tools) 的能力時，防護網就成為了不可或缺的救命索。在實務上，這主要有兩種不同的治理思路：

- **CLI (命令列工具)**：授權 AI 在本地端直接執行 Bash 指令。這雖然是效率極高的做法，但也是一把極度危險的**雙面刃**，因為模型擁有了太大的自由度，容易引發不可控的風險。
- **MCP (Model Context Protocol)**：目前業界更推崇的一套全球統一工具接入標準。它具備**強結構化**與**高安全性**的特性。透過 MCP 框架，AI 只能調用「事先定義好並授權」的特定 API，無法做出越軌行為。這就是護欄最直接的展現。

除了工具權限，完整的護欄系統也會強制對 AI 輸出的文字進行打磨，確保最終回傳給軟體的字串完全符合特定格式，且毫無機密外洩的風險。

### 2. 給予行為規範的「入職手冊」(Skill Definitions)
在賦予 AI 工具後，它充其量只是個「有手有腳的機器人」。為了解決這個問題，我們可以撰寫 **SKILL (技能)** 檔案，把它當作新進員工的入職手冊，將任務嚴格封裝。

一份合格的 `Skill.md` 通常必須明確畫出底線，例如：
```markdown
# 執行原則
- **數據準確性**：所有數值必須透過執行相對應腳本獲取，嚴禁模型依靠本身知識庫自行編造數字 (Hallucination)。
- **格式優先**：優先詢問用戶需要的檔案格式 (CSV 或 PDF)，嚴禁隨意變更。
```
透過這樣明確的技能治理，Agent 在執行任務時才有所依循，不會因為過度發散的「思維鏈」而鑽牛角尖或導致錯誤決策。

### 3. 系統化評估機制 (Evals & Systematical Testing)
這呼應了 OpenAI 給開發者的一項黃金建議：**「有系統地測試變化 (Systematically test changes)」**。傳統寫 Code 靠單元測試；在開發 AI 系統時，我們則依賴 **Evals (評估)**。

- **建立黃金標準 (Gold Standard)**：準備多道包含了邊緣案例 (Edge cases) 與惡意提示詞 (Jailbreak) 的標準測試集。
- **自動化測試管道 (CI/CD for LLMs)**：任何一次 Prompt 或系統邏輯的修改，都必須讓它自動跑過這套測試集。
- **常見的評分維度**：
  - _正確性 (Accuracy)_：回答是否與設定的真實標準答案匹配？
  - _工具調用率 (Tool Accuracy)_：在該用腳本查詢時，它是否確實調用了工具，還是自己胡謅答案？
  - _語義無關性 (Relevance / Hallucination)_：它的回答是否偏題？

## 三、主流工具與實踐
在實務中，有許多框架與平台正在協助開發者打造強固的 Harness：
- **LangSmith / Langfuse**：專門針對 LLM 呼叫紀錄追蹤、效能監控與 Evals 評分的平台，讓「黑盒子」的 AI 生成過程變得具象且可視。
- **NeMo Guardrails**：NVIDIA 開源的對話護欄系統，能即時攔截並糾正不符規範的對話。
- **MCP 架構**：正如前述，採用標準化協定就是建立安全介接點的最佳實踐。

## 四、思維轉變：從「基礎建造」到「駕馭引導」

幾經摸索後，我們會發現一個重要觀念：對於一般開發場景而言，**我們其實不需要從零開始打造所有的底層基礎設施**。

現在的主流 AI 平台（如 ChatGPT、Gemini 等）在背後**早就自動實作了龐大的現成治理架構**，這包含了：
- **運行基礎**：上下文管理 (Context Management)、提示詞緩存 (Prompt Caching)、記憶系統。
- **安全護欄**：沙箱系統、權限控制、Hooks 攔截、注入防禦。
- **擴充生態**：子 Agent、協作團隊 (Teams)、技能 (Skills)、外掛 (Plugins)。

既然平台已經扛下了最困難的「底層防護與記憶管理」工作，身為使用者的我們，焦點就應該發生轉移——**不再是著重於「如何硬著頭皮刻出一個護欄系統」，而是「我們如何去駕馭 (Drive) 並引導這些平台，來精準完成我們的工作需求」**。

這種「駕馭」建立在你如何將你的**個人習慣**傳遞給它，如何透過撰寫一份完善的 `Skill.md` 來與 Agent 順暢溝通，讓這些強大的 AI 引擎精準地為你效勞。

### 實戰分享：我是如何駕馭「記憶對齊」 (建立任務存檔點)
在實際的日常開發情境中，由於對話視窗有生命週期限制（會遇到 Context Window 被重置的狀況），我會透過以下方式主動去駕馭平台的「記憶系統」：

1. **工作告一段落時（存檔）**：
   在結束工作前，我會請平台把剛剛完成的階段性事項做一個總結紀錄，並將其寫入到專案中的特定檔案（例如 `歷史.md` 或 `工作紀錄.md`）。這個步驟等於是手動讓大模型把短暫的對話快取，提煉並固化成了實體的長期記憶檔案。
   
2. **下次開啟專案時（讀檔）**：
   當新的工作開啟時，我不需要老調重彈。可以直接命令平台去讀取 `工作紀錄.md`。由於現在的平台擁有強大的上下文讀取能力，它能在瞬間掌握「上次實作到哪裡、目前的狀態是什麼」，並明白接下來要處理哪幾個檔案。隨後只要讓它掃描那幾個檔案，就能無縫接軌進行下一次的開發循環。

利用這種「手動存檔與讀檔」的工作習慣，就是「不瞎造輪子，而是巧妙指引 Agent 自動化流程」最好的駕馭範例。

### 業界實證：Anthropic 的 Harness Design 與專案 Init 機制
上述的習慣與做法，實際上已經與頂尖 AI 實驗室的發展方向完全疊合。Anthropic（開發 Claude 的公司）近年來大力提倡 Harness Engineering 的概念，並在他們官方的 Claude Code (CLI 開發助理) 中，內建了印證這套哲學的機制：

1. **專案初始化指令 (`/init`)**：
   Anthropic 為了省下開發者重新描述上下文的心力，導入了 `/init` 功能。在專案中執行此指令時，它會掃描環境並建立諸如 `CLAUDE.md` 這樣的指示檔（這**完全等同於**我們上段提到的 `工作紀錄.md`）。
   
2. **自動化的上下文本底化**：
   一旦專案有了 `CLAUDE.md` 以及其專屬規則目錄（如 `.claude/rules/`），未來每次 AI 介入專案時，都會**自動優先讀取**這些檔案。系統馬上就能知道你採用的框架、目前的進度、以及有哪些可調用的 MCP 配置。

這個發展證實了：現代的系統架構正全盤吸收底層 Harness 的工作。我們實踐 Harness Engineering 的終極手段，就是善用像 `/init` 或自建 `歷史.md` 這類約定俗成的機制，去完美牽制並引導 AI。

### 框架化駕馭：OpenSpec 與 SpecKit 
為了將這套「靠習慣與紀錄檔來驅動」的模式更進一步標準化，現在的開源社群也發展出了 **SDD (Spec-Driven Development, 規格驅動開發)** 的專屬 AI 框架，最有名的包含 **OpenSpec** 與 **SpecKit**。

它們的初衷主要是為了解決過度依賴對話視窗所導致的「發散編程 (Vibe Coding)」與「上下文腐敗 (Context Rot)」：
- **將規格視為契約**：與其丟給 AI 一大段無結構的長文，OpenSpec 提倡建立輕量資料夾（設立 `specs/` 存放規格真相，`changes/` 存放變更提案）。這種做法正是任務紀錄檔概念的進階版。
- **流程門檻 (Gated Workflow)**：SpecKit 則定死了 AI 協作的工作流指令（例如先 `/specify` 定義需求 -> 再 `/plan` 計畫 -> 最後 `/implement` 寫程式）。大模型必須先在 Markdown 裡與人類核對完架構與步驟，獲得批准後才能動手去改 Code。

這就是在專案中立起了一層 **「宣告式的程式契約」**。開發者只需負責審視和修改那本規格文件，剩下的就能放心交給大模型去執行，確保產出的程式碼不會偏離航道。

### 另一種哲學：為了解決程式碼潔癖的「記憶資料庫架構」
最後，值得探討的是：**雖然建立一堆 `.md` 檔案來管理上下文是當前最常見的作法，但許多開發者其實認為這種做法挺「髒」的。**  我就這樣覺得，我不喜歡AI在我的電腦到處丟垃圾。

因為這會導致專案資料夾裡混入許多沒有實際編程意義的內容，這些多出來的訊息純粹只是為了給 AI 帶路，強行參雜在專案資料夾中。對於有程式碼潔癖的我來說，這並不是一個完美的解法。

所以如果你跟我一樣更偏向將「AI 的記憶與指令」從「純粹的原始碼專案」中抽離出來，可以參考開源社群發展的多套**專屬 AI 記憶資料庫專案**：

1. **Mem0 (前名 Embedchain)**：
   這是一個生產就緒的開源記憶層 (Memory Layer)。它主張將 Agent 的記憶從專案資料夾中抽離出來，改用向量資料庫與知識圖譜統一存放。AI 運作時是透過 API 向 Mem0 系統詢問「這個專案目前的開發進度」，而不是在 Repo 裡掃描 Markdown 檔案。
   
2. **Letta (前名 MemGPT)**：
   這套框架的架構深受傳統作業系統啟發。它將 LLM 珍貴的 Context Window 當成「記憶體 (RAM)」，而將龐大的專案歷史與工作準則放在外部獨立資料庫當作「硬碟」。它賦予了模型自主「分頁調度 (Paging)」的能力去讀寫硬碟記憶，讓你的專案目錄能持續保持極度乾淨。
   
3. **Cognee**：
   這是一套能將我們非結構化的對話總結與任務狀態，轉化為關聯式知識圖譜 (Knowledge Graph) 獨立儲存的框架。

採用這些開源資料庫來管理 Context 與 Skill，優點是能完美做到**「關注點分離」**與維持專案整潔。當然，代價就是架構變重，必須額外維護記憶伺服器。無論是選擇「文件跟著程式碼走的 Markdown 派」，還是「記憶交給伺服器託管的 Database 派」，這都是在實踐 Harness Engineering 時可以思考的進階選擇。

## 總結
Harness Engineering 就是將「AI 玩具」淬鍊成「AI 產品」的關鍵。如果我們要自己從底層開發一套 AI 系統，就需要用最嚴謹的軟體工程去把關；但當我們站在這群科技巨人的肩膀上使用現成的主流平台時，核心價值就變成了：**我們能否設定清晰的工作邊界，並熟練地駕馭它。** 唯有透過明確的規則與指引，這股強大的 AI 能量才不會在代碼的荒野中迷失，而是精準、安全地為我們創造價值。

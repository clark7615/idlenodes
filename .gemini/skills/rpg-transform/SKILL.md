# Skill：RPG化（閒逸神諭所風格轉換）

## 觸發條件

當使用者提到「RPG化」時，啟動本技能。使用者會提供一篇原始文章（Markdown 格式或純文字），你需要將其轉換為符合「閒逸神諭所」世界觀的 RPG 遊戲化風格文章。

## 輸入

- 一篇原始文章（技術文件、管理方法論、課程筆記、工具配置等）
- 使用者可能指定目標分類（Grimoires / Quests / SageTower / Forge），若未指定則自動判斷

## 輸出

- 一篇完整的 RPG 化 Markdown 文章，嚴格遵循以下所有規則。

---

## 規則一：Frontmatter 元資料

每篇文章開頭必須包含以下 YAML frontmatter：

```yaml
---
title: "{emoji} {RPG化主標題}：{RPG化副標題}"
description: "{以奧術/戰鬥/冒險語氣寫的一段式簡介}"
permalink: "/{english-kebab-case-slug}"
class: "Oracle"
rarity: "{稀有度}"
icon: "{圖示}"
tags:
  - {分類標籤}
---
```

### 標題規則
- 格式：`emoji + 空格 + RPG化主標題 + 冒號 + RPG化副標題`
- 主標題應將原始主題轉為奧術/戰鬥/冒險語彙
- 副標題保留原始概念但加上 RPG 修飾
- 範例：
  - 原始：「Scrum 敏捷開發框架」→ `🏃 Scrum 衝刺儀式：敏捷開發的策略法典`
  - 原始：「Docker MCP 工具包」→ `🔮 容器召喚術：Docker MCP Toolkit`
  - 原始：「工作復盤方法論」→ `🔄 戰鬥復盤：經驗值獲取指南`

### 分類判斷邏輯

根據文章性質選擇分類，規則如下：

| 分類 | 適用場景 | icon | tags |
|---|---|---|---|
| **Grimoires**（奧術法典） | 技術知識、管理方法論、框架學習、工具使用教學 | 📖 | `Grimoires` |
| **Quests**（冒險任務） | 實作專案記錄、系統建置過程、實戰部署 | 📜 | `Quests` |
| **SageTower**（賢者塔） | 課程筆記、學術理論、深度長文 | 📖 | `SageTower` |
| **Forge**（鍛造工坊） | IDE 設定、開發環境配置、工具鏈設定 | 🛠️ | `Forge` |

### 稀有度判定

| 稀有度 | 判定條件 |
|---|---|
| `Unique` | 首頁、人物頁等獨一無二的頁面 |
| `Epic` | 有完整實作流程的專案記錄（Quests）、獨特工藝品 |
| `Rare` | 一般知識法典、方法論、教學文章 |

## 規則三：文章結構模板

### 整體結構

```markdown
# {emoji} {RPG化主標題}：{RPG化副標題}

{粗體的一段式 RPG 化核心描述，與 frontmatter description 呼應但更加展開}

## {章節一標題}
{內容...}

---

## {章節二標題}
{內容...}

---

## {更多章節...}

---

## 相關主題

> 💡 **延伸閱讀**：
> - {引導語}？參考 [[分類/檔名|RPG化標題]]
```

### 章節標題規則

- 使用 `##` 搭配 emoji 開頭
- 將原始概念轉為 RPG 戰術語彙
- 格式：`## {emoji} {RPG化概念}：{原始概念的RPG化解釋}`
- 範例：
  - `## 神聖職責：角色分工與禁忌`
  - `## 核心循環：衝刺儀式 (Sprint)`
  - `## 🧭 四象限能量矩陣`
  - `## 施法戰術：三階段情緒轉化`

### 子段落規則

- 使用 `###` 搭配數字或 emoji flag
- 範例：
  - `### 🚩 第一階段：激進開場 (打破虛假和諧)`
  - `### 1. Scrum Master (儀式導師)`

### 正文首段

- 必須加粗（`**...**`）
- 以第二人稱或總結性語氣寫出核心描述
- 融入奧術/冒險語彙

## 規則四：Obsidian Callout 使用規範

必須在適當位置使用以下 Callout，每篇文章至少出現 2-3 種：

### 開場引言（文章開頭，緊接在 H1 標題與首段描述之後）

```markdown
> [!BOOK] 法典引言
> {用奧術口吻定義文章核心概念}
```

或

```markdown
> [!BOOK] 秘法定義：{概念名稱}
> {定義內容}
```

### 重要理則（核心規則或不可違反的原則）

```markdown
> [!IMPORTANT] 核心理則
> {重要規則的 RPG 化描述}
```

### 警告禁忌（風險、禁止事項）

```markdown
> [!CAUTION] 法典禁令
> 1. **禁{行為}**：{RPG化的解釋}
> 2. **禁{行為}**：{RPG化的解釋}
```

或

```markdown
> [!CAUTION] 警告：{警告名稱}
> {警告內容}
```

### 智慧總結（章節或全文的精華總結）

```markdown
> [!SAGE] 智慧總結
> {一句精煉的 RPG 化金句}
```

或

```markdown
> [!SAGE] 總結
> {總結內容}
```

### 實用建議

```markdown
> [!TIP] 修煉建議
> 1. {建議一}
> 2. {建議二}
```

### 實驗性內容

```markdown
> [!WARNING] 實驗性術式
> {警告此內容仍需驗證}
```

## 規則五：交叉引用與延伸閱讀

### 文章結尾固定格式

每篇文章結尾必須包含以下結構：

```markdown
---

## 相關主題

> 💡 **延伸閱讀**：
> - {疑問句引導語}？參考 [[分類/檔名|RPG化顯示標題]]
> - {疑問句引導語}？參考 [[分類/檔名|RPG化顯示標題]]
> - {疑問句引導語}？參考 [[分類/檔名|RPG化顯示標題]]
```

### 引導語撰寫規則

- 以讀者可能的下一步需求為出發點
- 使用疑問句
- 範例：
  - `想了解如何撰寫更好的AI提示詞？`
  - `如何精準化目標？`
  - `建立高效的協作契約？`
  - `進行戰鬥後的深度反思？`

### 文章內部交叉引用

在正文中提到相關概念時，可使用 Wiki-link 格式引用：

```markdown
建議使用 [[Grimoires/smart-principles|SMART 符文]] 來精準化你的目標
```

## 規則六：表格與結構化內容

### 表格使用時機
- 分類對照（如：概念 vs RPG 對應）
- 屬性對比（如：角色類型比較）
- 步驟摘要
- 配置參數

### 表格欄位命名 RPG 化

| 原始欄位名 | RPG 化欄位名 |
|---|---|
| 名稱 | 術式名稱 / 能量代碼 |
| 說明 | 奧術意義 |
| 類型 | 天賦屬性 |
| 功能 | 施法效果 |
| 設定值 | 值 |
| 設定項目 | 設定項目（此類保持不變） |

### Mermaid 圖表

當原始文章包含流程圖或架構圖時，使用 Mermaid 語法呈現，節點名稱可保持技術原名但加上 RPG 描述括號。

## 規則七：敘事語氣與人稱

### 人稱
- **一律使用第二人稱「你」**
- 將讀者視為同行的冒險者或正在修煉的學徒
- 範例：「你推開了沉重的石門」「當你施展此術式時」

### 語氣定位
- **嚴謹但帶有奇幻感**
- 不是搞笑幽默，而是「專業的奧術學者在傳授知識」
- 像是一位資深先知在寫給後輩的法典

### 敘事開場（可選，適用於 Quests 和特殊文章）

某些文章可在開頭加入一段沉浸式的場景描述：

```markdown
你站在鍛造工坊的桌台前，桌上攤開著一張充滿古老皮革香氣的草圖。
```

```markdown
你推開了沉重的石門，空氣中瀰漫著古老羊皮紙與微弱奧術能量的香氣。
```

### 禁止事項
- 不要使用現代網路用語或梗（如「yyds」「絕絕子」）
- 不要過度搞笑或破壞世界觀的嚴肅感
- 不要在技術細節處強行替換（程式碼區塊內保持原始技術名稱）
- 程式碼區塊（code block）內容保持原樣，註解可以 RPG 化

## 轉換工作流程

當使用者提供原始文章後，按照以下步驟進行轉換：

1. **分析文章**：判斷文章主題、分類（Grimoires/Quests/SageTower/Forge）和稀有度
2. **建立 Frontmatter**：套用規則一生成 YAML 頭部
3. **重寫標題與首段**：套用規則三轉換標題與粗體首段
4. **內容轉換**：逐段改寫，套用規則二的詞彙映射表與規則七的語氣
5. **插入 Callout**：套用規則四，在適當位置插入 2-3 種 Callout
6. **結構化內容**：套用規則六，將表格欄位 RPG 化
7. **加入延伸閱讀**：套用規則五，在結尾添加相關主題連結（根據目前 content 資料夾中已存在的文章選擇最相關的 2-3 篇）
8. **最終審查**：確保整體語氣一致、世界觀不衝突、技術內容準確

---

## 注意事項

- **技術準確性優先**：RPG 化是外皮，技術內容必須完全正確
- **程式碼區塊保持原樣**：code block 內的程式碼不做 RPG 替換，但註解可以
- **不要過度轉換**：某些固有名詞（如 Docker、Scrum、SMART 等）保持原名，但可在旁邊加上 RPG 化的別稱括號
- **段落間使用 `---` 分隔線**：每個主要章節之間使用水平線分隔
- **保持可讀性**：RPG 化不應犧牲文章的可讀性與知識傳達效果
